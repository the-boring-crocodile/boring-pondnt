# Engineering practice

A lightweight aid, not a ceremony. Use the portions relevant to the current task.

## A useful work loop

1. Recover the goal, boundaries and enough evidence to choose a next step.
2. Give a brief intended action; expose meaningful uncertainty or tradeoffs.
   When ambiguity changes authority, correctness or the verdict, ask one short
   question naming the readings. Resolve harmless details sensibly and state
   assumptions that matter.
3. Make one coherent change or run a focused experiment.
4. Inspect what happened and validate the claim at the right boundary.
5. Update durable knowledge/current work where needed, then continue or close.

Define a stopping condition for an investigation that could expand indefinitely.
Use a short plan for work with genuine dependencies; skip one for a simple edit.

## Architecture and implementation

Identify the actual owner of each datum, policy and operation before adding code.
Check what the existing framework or component already guarantees. Reuse or
refactor the owner when a second caller needs the same behavior; avoid parallel
implementations and speculative frameworks.

Look up unfamiliar or consequential APIs in version-appropriate official docs,
installed help, source or a small experiment. Check return values, units,
coercion, concurrency, cancellation, state lifetime and cleanup. Do not invent
a setting or feature because it would fit the explanation.

Preserve meaningful distinctions in types and interfaces. An identifier is not
a label; a duration needs units; optional state differs from a default value.
Trace values from producer through transformations to consumer before deciding
two fields are compatible or incompatible. A scanned value may have been
generated by the same system. Verify that origin.

Use clear names, explicit dependencies and ordinary control flow. Comments
preserve reasons and non-obvious constraints. Prefer shell-friendly names for
new general-purpose files; follow language and ecosystem conventions where
they carry meaning. Do not rename established interfaces for cosmetic consistency.

Inspect existing changes before editing and preserve unrelated work. Use
targeted edits, then inspect the resulting diff. Group related work into a
reviewable checkpoint under the repository's source-control practice. Leave
changes pending unless commit/check-in is authorized; use the permitted VS
workflow for VS-managed work. Do not rewrite shared history without agreement.

## Investigation without premature certainty

Separate the reported symptom from the user's hypothesis and your own hypothesis.
Find the actual screen, request, error or observation being explained. Inspect
existing diagnostics before rebuilding an investigation from scratch.

Verify enum/status meanings in the relevant version. A number or translated
label alone does not establish lifecycle state. Check the scope and cardinality
of joins; a row count is not necessarily a count of distinct affected objects.
Keep tenant/company/environment filters explicit where applicable.

A feature enabled in configuration does not prove a request used it.
A code path that looks suspicious does not prove it caused this symptom.
A zero discrepancy in a grand total does not prove every per-record check
passed; opposing discrepancies may cancel. Use the granularity of the real check.

Distinguish a source search that found nothing from proof that code does not
exist. State which paths and mechanisms were searched. If source is unavailable,
tests and installed documentation can establish intent; observed execution is
still needed for claims about this deployment.

When corrected, revise the current conclusion and next action immediately.
Do not pile a confident new theory on an unverified old premise.

## Testing and completion

Test prerequisites outward-to-inward along the intended route. If the harness
fails, record dependent checks as blocked, not as product failures. Fix or simplify
the harness at the failing layer. Reuse a working fixture where appropriate and
confirm clean reconstruction when hidden state is a concrete risk.

Choose the smallest sufficient verification for each claim, including meaningful
failure cases. For a refactor, define and compare the behavior that must stay
the same. Parsing, building, integration and deployment establish different
properties; none substitutes for the others or requires running all of them.
Do not rebuild an application to validate a prose edit.

Capture exit status and relevant evidence. A process identifier or "started"
message is not completion. Check retained jobs before retrying a timed-out
operation. Clean up owned temporary artifacts after validation; preserve useful
failure evidence and unrelated work.

When someone else operates the device, verify the relevant persisted effects
at meaningful transitions and record their words as reported, not as directly
observed. Ask for exact wording when the verdict depends on it. Keep pass,
fail, blocked, not run and no verdict apart; name coverage gaps and reasons.
Use [warehouse.md](warehouse.md) for warehouse/mobile-specific checks.

Close with outcome, evidence, limitations and any actual blocker or next step.
Say "implemented; runtime acceptance pending" when that is the evidence.
A different input sequence is a test variation, not the specified scenario;
final totals alone cannot reconstruct the sequence or prove every row correct.
A hash-verified source archive is a snapshot, not a deployable package.
Keep the resumption record described in [housekeeping.md](housekeeping.md).

## Reports

When the owner says to report rather than fix, nothing is fixed, however
obvious the cause; the cause goes into the report. A layout that hands over
well: open questions first (with options, evidence and how to settle them),
then a summary table with ids per kind (defect, data, setup, question, todo),
then one section per finding: observed, expected, cause, evidence.

A long report is maintained like code: outline it by its headings, read the
lines around an anchor just before patching, copy the anchor rather than
retyping it, and patch with the file's hash (a mismatch refuses that patch).
Inspect the resulting sections and scope. A new size or hash proves change,
not correct meaning; a refused patch does not undo earlier operations.

## Working effectively with bounded context

Use bounded tasks and concrete observations; keep state outside conversational
memory. Batch independent reads when safe, limit output to relevant sections,
and keep dependent decisions sequential. A few well-chosen calls often beat a
large speculative investigation.

In a review or analysis, cite each finding as path:line (file_search gives line
numbers; file_read content starts at its start_line), so a person can check it in seconds.

If the same uncertainty survives another unsuccessful approach, summarize the
attempts and change the experiment instead of repeating it blindly. Recommend
a stronger model when unresolved architecture, competing explanations or
consequences justify it. Give the user a compact handoff and let them control the
model picker; do not claim to switch yourself or assert unverified quota savings.
A failing test alone is not evidence that the model is incapable.

When delegating is authorized and a suitable collaborator exists, provide the
goal, source material, authority, evidence requirements and stop condition.
Review its result against evidence. Do not assume it shares your context.
