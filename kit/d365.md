# D365 development

Read for X++, model changes or D365 investigation. Read
[warehouse.md](warehouse.md) for warehouse/mobile work and
[visualstudio.md](visualstudio.md) before managing source, builds or the IDE.

## Find the owner before coding

Identify application/platform version, model, owning package, dependencies,
prefix and current source. Standard Microsoft and vendor elements are inspected,
not modified. Extend them from the project's model; edit your own elements
directly when appropriate. Do not introduce a new extension layer for an
ordinary change to a class the project already owns.

Use metadata extensions for fields, indexes, relations and supported form
structure. Add table methods through augmentation classes; do not put methods
into a metadata extension as if it were the original element.
See [table augmentation](https://learn.microsoft.com/en-us/dynamics365/fin-ops-core/dev-itpro/extensibility/add-method-table).

For Chain of Command (CoC), read the target method first. Use this shape
(replace the example target, prefix and method with the actual ones):

```xpp
[ExtensionOf(classStr(Target))]
final class Target_PFX_Extension
{
    public void execute()
    {
        next execute();
        // Add the required post-operation behavior here.
    }
}
```

Match the signature and static/instance form; omit parameter default values.
Call `next` exactly once, unconditionally. Do not put it in an if/loop or return
before it. A `[Replaceable]` target permits a deliberate conditional break.
Private methods cannot be wrapped. Final methods need `[Wrappable(true)]`;
`[Hookable(false)]` or `[Wrappable(false)]` forbids wrapping.
Use `tableStr(T)`, `formStr(F)`, `formDataSourceStr(F, DS)` or
`formControlStr(F, C)` inside ExtensionOf for those targets. For nested form
targets, check that the method is wrappable on that control/data-source type.
Do not assume extension order.
See [CoC](https://learn.microsoft.com/en-us/dynamics365/fin-ops-core/dev-itpro/extensibility/method-wrapping-coc).

Create public static event-handler methods in your model. Use the IDE-generated
signature for the selected event/delegate:

- Delegate: `[SubscribesTo(classStr(X), delegateStr(X, d))]`.
- Table: `[DataEventHandler(tableStr(T), DataEventType::Inserting)]`.
- Form: `[FormEventHandler(formStr(F), FormEventType::Initializing)]`.

Prefer CoC when you need the method's return value or instance context.
See [extension examples](https://learn.microsoft.com/en-us/dynamics365/fin-ops-core/dev-itpro/extensibility/customize-model-elements-extensions),
[delegate binding](https://learn.microsoft.com/en-us/dynamics365/fin-ops-core/dev-itpro/dev-ref/xpp-events)
and [form initialization](https://learn.microsoft.com/en-us/dynamics365/fin-ops-core/dev-itpro/office-integration/customize-open-office-menu).

Search cross-references and current source before renaming, changing signatures
or choosing an extension point. Index age/coverage and compiled references
limit the conclusion: no match is not proof of no caller or no installed API.

## Data semantics

- Write user-visible text as `"@<LabelFile>:<Id>"`. Use `label_lookup` to
  find an existing label; reuse only an exact meaning. Otherwise add one in
  the project's label file through the permitted IDE route.
- Use the appropriate EDT, size, enum, unit and identifier. Do not infer the
  meaning of a number, translated label or scanned string without tracing it.
- Respect the caller's transaction. Select-for-update and update/delete must
  use the appropriate same transaction scope. Do not scatter independent
  commits or swallow errors to make a workflow continue.
  See [X++ transactions](https://learn.microsoft.com/en-us/dynamics365/fin-ops-core/dev-itpro/dev-ref/xpp-data/xpp-transaction).
- Identify company-specific versus shared tables. X++ company context,
  changecompany/crossCompany and raw SQL have different semantics. Explicitly
  establish the intended legal entity; the same document number can recur.
- Use standard inventory dimension and business-process APIs. Verify the
  required quantity, unit, dimensions and lifecycle; a header total is not
  interchangeable with transaction or on-hand detail.
- Business dates and timestamps are different. Preserve the domain's date/time
  type and timezone semantics. Use the established number-sequence framework
  instead of inventing counters.
- Preserve metadata serializer order. The AOT deserializer is order-sensitive
  in 10.0.48/10.0.49: an out-of-order property can be silently dropped while XML
  parsing and compilation pass. For example, AxTableField puts
  `ExtendedDataType` before `HelpText` and `Label`; derive the complete order
  from a designer-saved element of the same type. Give string fields the
  appropriate EDT/size: a dropped EDT left affected fields at String 10.
  Have VS save/reopen the element, compare the properties, then check the actual
  width with `sys.columns` after sync. A clean build alone is insufficient.
  Found in the standard source and confirmed at runtime for those two
  versions; check again on another version.

## Development and acceptance

Use the VS workflow for source, project membership, build and relevant sync/BP
checks. Read diagnostics for the actual candidate. A file parse, designer view,
build, sync and real run establish different properties. Perform the smallest
sufficient checks for the change, with meaningful failures as well as success.
After an import failure, empty or malformed element files are useful suspects;
inspect evidence before declaring a cause.

A stopped IIS service does not establish a stopped application: VS may host
IIS Express. Establish who owns the running application before proposing any
restart. Restarting interrupts sessions/debugging and requires authorization.

For a feature, choose relevant acceptance cases: intended and wrong company,
realistic user role, repeated action/retry, transaction failure, labels, real
form/device behavior and integration effects. Unconfigured event endpoints,
missing security roles or unexecuted cases remain named coverage gaps.

Test helpers use appropriate application initialization, validation and write
APIs; validateWrite alone is not a complete business-process implementation.
Make reruns safe, identify exactly what they reset, and preserve unrelated data.
Do not post, receive, complete work or confirm by changing status fields in SQL.
Data inspection and bounded direct test-data exceptions: [tools.md](tools.md).

Deployment, recovery and cleanup are engineering too. A helper or operational
script needs an owner, clear effects, failure behavior and proportionate evidence.
An untested recovery stays an assumption.

## Sources and claims

Use sourcecache for indexed source/labels and xref for compiled relationships.
Check version, scope and index age before relying on either. Locate newer or
unindexed code through the authorized IDE/read-only route; do not widen access.
Cite element, index/version and returned file lines. XML file lines are not
VS X++ editor lines.

Use Microsoft Learn search/fetch if available, otherwise official documentation
through an available authorized route. Separate retrieved documentation, local
source, observation and recollection. If they disagree, investigate the version
and path; do not force the deployment to match an article.
